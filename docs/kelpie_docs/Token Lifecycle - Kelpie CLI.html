Token Lifecycle

How Kelpie keeps your tokens fresh without you lifting a finger.

Once you’ve logged in, Kelpie manages your tokens behind the scenes — caching, refreshing, and reusing them so you never have to think about expiry or re-authentication.

How tokens flow

After a successful login, Kelpie stores two tokens:

TokenPurposeLifetime
Access tokenA JWT that proves your identity to platform servicesTypically 1 hour
Refresh tokenA long-lived credential used to get new access tokens24 hours or until revoked

When you (or the proxy) need a token, Kelpie checks the stored access token first. If it’s still valid, you get it back immediately — no network calls, no waiting. If it’s expired, Kelpie uses the refresh token to silently grab a new one.

Where tokens are stored

Kelpie stores tokens on disk in your platform’s standard config directory:

PlatformPath
Linux~/.config/kelpie/credentials.json
macOS~/Library/Application Support/kelpie/credentials.json
Windows%APPDATA%\kelpie\credentials.json

The credentials file is created with 0600 permissions (owner read/write only), and the directory with 0700. Each account’s credentials are stored independently, keyed by email address.

Refresh flow

When an access token expires, Kelpie doesn’t ask you to log in again — it uses the refresh token to get a new access token automatically:

  1. Kelpie sends the refresh token to the OIDC provider’s token endpoint
  2. The provider verifies the refresh token and issues a new access token
  3. Kelpie stores the new token and continues as if nothing happened

The proxy daemon does this proactively — it checks every minute and refreshes 5 minutes before expiry, so there’s never a gap where your token is invalid.

If you’re using kelpie auth print-access-token, the same logic applies: if the stored token has expired, Kelpie refreshes it first and then prints the new one.

When refresh fails

Refresh tokens can be revoked — for example, if an administrator disables your account or if you logged out from another session. When this happens:

  • Proxy daemon: logs the error, pauses her background refresh, and sends a desktop notification — “Your session has expired. Log in again to continue.” The status dashboard shows “Your session ended”, and once your current access token runs out, requests through the proxy get a 401 with a message to log in again. As soon as you sign in again, she picks up refreshing on her own — no restart needed
  • CLI commands: return an error asking you to log in again

If the refresh fails because of a network issue (VPN disconnected, server unreachable), the proxy handles it differently — she keeps retrying with backoff and sends a notification letting you know to check your connection. Once the network comes back, she picks up automatically.

In any case, you can log in again from the status dashboard or by running kelpie auth login from the terminal. See Desktop Notifications for the full list of notification messages.

Multi-account storage

Kelpie supports multiple accounts simultaneously. Each time you log in, the new account becomes the active one, but previously stored accounts keep their credentials. The credentials file looks like this:

{
  "alice@example.com": {
    "access_token": "eyJ...",
    "refresh_token": "refresh_...",
    "token_type": "Bearer",
    "expiry": "2026-05-29T15:30:00Z"
  },
  "bob@example.com": {
    "access_token": "eyJ...",
    "refresh_token": "refresh_...",
    "token_type": "Bearer",
    "expiry": "2026-05-29T16:00:00Z"
  }
}

A separate config.json file tracks which account is currently active. When you log in or out, Kelpie updates this file automatically.
