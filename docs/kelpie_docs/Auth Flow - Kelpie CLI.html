Auth Flow

A peek behind the curtain — how Kelpie logs you in so you don’t have to think about OAuth.

Kelpie uses the OAuth 2.0 Authorization Code flow with PKCE (RFC 7636) to authenticate you with the DARE platform. The platform’s OIDC service at oauth.ai.container.edag delegates the actual sign-in to Microsoft Entra. You absolutely don’t need to understand every detail on this page to use the CLI, but we’ve written it all out here for when you’re curious or need to debug something.

Overview

Here’s what happens when you run kelpie auth login:

  1. Kelpie generates a random PKCE code verifier and its SHA-256 challenge
  2. It starts a tiny HTTP server on your machine to listen for the callback
  3. Your browser opens to the OIDC service, which redirects you to Entra for sign-in
  4. After signing in, you’re redirected back to Kelpie’s local server with an authorization code
  5. Kelpie exchanges that code (plus the original verifier) for an access token and refresh token
  6. The access token’s signature and claims are verified against the issuer’s public keys
  7. Your tokens are stored securely on disk — and you’re in!

Why PKCE

In a traditional authorization code flow, a client secret is used to prove identity during the token exchange. But Kelpie is a public client — she runs on your machine, not on a server — so there’s no safe place to store a secret.

PKCE solves this elegantly. Instead of a static secret, Kelpie generates a unique one-time proof for every login:

StepWhat happens
Before loginKelpie generates a random code_verifier (43 characters of cryptographic randomness) and computes code_challenge = BASE64URL(SHA256(verifier))
AuthorizationThe challenge travels with the browser request to the OIDC service, which hands the sign-in over to Entra
Token exchangeThe original verifier is sent to the token endpoint, which checks that SHA256(verifier) matches the stored challenge

Even if someone intercepts the authorization code, they can’t exchange it without the verifier — which never left your machine.

State parameter

To prevent cross-site request forgery (CSRF), Kelpie generates a random state value alongside the PKCE verifier. When the callback arrives, Kelpie checks that the returned state matches the one it sent — if it doesn’t, the login is rejected immediately. This makes sure the callback is genuinely a response to your login attempt and not a malicious redirect.

The local callback server

When you run kelpie auth login, a small HTTP server spins up on 127.0.0.1 with a random port — it only listens on the loopback interface, so nothing outside your machine can reach it. The server:

  • Validates the state parameter against CSRF attacks
  • Receives the authorization code from the browser redirect
  • Waits for the token exchange and verification to complete before responding
  • Shows a friendly success or error page in your browser

The server shuts down automatically as soon as the flow is complete. If no callback arrives within 2 minutes, the login times out.

Token verification

After exchanging the authorization code for tokens, Kelpie doesn’t just trust the response blindly. It verifies the access token by:

  1. Fetching the issuer’s JSON Web Key Set (JWKS) — the public keys used to sign tokens

  2. Finding the key that matches the token’s kid (key ID) header

  3. Verifying the RS256 signature

  4. Checking the standard JWT claims:

    ClaimWhat Kelpie checks
    issMatches the issuer from the discovery document
    audPresent and non-empty (validated by target services)
    expToken hasn’t expired
    iatPresent
    subPresent and non-empty
    jtiPresent (unique token identifier)

  5. Extracting the custom DARE claims (your email, display name, role, project, and allowed models)

Only after all checks pass does Kelpie store your credentials and report a successful login.

What the server sees

For the curious — here’s what the token exchange looks like from the management service’s perspective:

POST /oauth/token
Content-Type: application/x-www-form-urlencoded

grant_type=authorization_code
&code=<authorization code>
&code_verifier=<PKCE verifier>
&redirect_uri=http://localhost:<port>/callback
&client_id=kelpie-cli

The server verifies the PKCE challenge, validates the authorization code, and hands back an access token and refresh token. That’s the entire exchange — one request, one response.
